# 开发基线核查记录（2026-11-07）

本记录对应开发计划 BASE01、BASE03 的首轮核查，以及统一注册方案的前置分析。静态发现不等于运行验收；本文件不含真实患者数据。113.44 的代码证据来自本地问卷系统，线上版本和配置需在实施与发布前另行核对。

## 登记与身份

已确认的产品方向：113.44 统一账号；医护邀请或申请后经中心管理员审核；患者可注册，档案及受试者关联经核实后生效。账号注册本身不授予医生权限、患者数据访问权或项目入组资格。统一账号、临床患者和项目受试者是不同对象。

现有113.44本地注册流程有邮箱验证和普通账号创建，项目成员模型有中心、角色、有效期及状态；管理员可直接指派项目成员。但现有注册中的机构关联不能作为医护身份审核，项目角色也不能直接等同于医生或患者；未发现完整的医护邀请/申请审核、患者本人账号与患者档案稳定绑定、面向medicalassistant的身份提供接口。匿名问卷邀请也不是医护入组邀请。

已形成[统一身份与授权契约草案](./identity-integration-contract.md)，覆盖注册审核、账号与患者/受试者映射、患者自填和医护代填、嵌入会话及撤权。本地身份提供接口和上线切换仍未实现，草案不代替真实接入验收。

后续应先冻结用户主体与授权契约，区分患者自填/医护代填，保留申请待审、拒绝、撤回、过期、账号停用和审计；核实历史账号兼具多种身份的情形。医护审核责任人、患者本人/监护人核验方式、身份协议及授权过期策略仍按开发计划 D02/D04/D11 确认，不能凭现有机构名或注册成功自动赋权。本轮未变更113.44线上或患者数据。

## 领域收敛前的代码基线

1. [健康档案 schema](../backend/app/schemas/health_record.py) 同名健康档案和随访模型重复定义，后定义覆盖前定义；服务访问的部分字段与最终模型不一致。应整理唯一契约并以实测数据核对，不能简单覆盖或删除集合。
2. [健康档案服务](../backend/app/services/health_record_service.py) 与 [医生路由](../backend/app/api/routers/doctor_router.py) 读取的随访集合不一致；康复服务与模型的计划集合也不一致。需先盘点数据库与访问路径，再确定统一 repository、迁移及兼容策略。
3. 健康档案路由未完整注册，路由顺序及权限 dependency 写法有潜在问题；直接 `include_router` 无法证明权限和行为正确。医护角色路由及随访页面存在假ID、空响应和模拟数据。
4. 康复反馈前后端路径和方法不一致；模型生成/保存失败可能返回模拟计划或临时ID。正式业务链应明确失败状态，避免将模拟结果作为个体化方案。
5. 本地 `DEBUG` 环境变量存在与项目 boolean 设置不兼容的情况，启动前应使用项目受控配置或报告明确错误，不能更改系统全局变量。

这些问题属于架构收敛范围，不能将单个路由补丁视为闭环。优先形成真实 MongoDB 的只读集合清单及调用图，确认唯一领域模型和授权边界，再在独立测试数据上验证“创建—查询—提交—医护审核—复评”。

## 运行和验证边界

项目依赖默认后端5502、前端5501和MongoDB；旧启动/停止脚本有跨项目进程影响，不能直接使用。环境搭建和启动脚本改造以项目私有进程、显式端口、真实HTTP和数据库健康为验收依据；端口被占用时应明确失败。数据库由独立生命周期管理，测试实例不能被描述为生产环境或持久化数据服务。

首次依赖核查：后端已在项目内 Python 3.12.8 虚拟环境安装声明的依赖；前端严格 `npm ci` 曾遇到 React 18 与 `react-json-view` 的 peer 版本冲突，替换兼容的同源维护组件后严格安装通过，并以真实组件的隔离浏览器测试验证只读JSON树。组件测试使用测试数据，并不代表真实后台业务闭环已通过。

前端原文件 `components/Agent/AgentForm.tsx` 首行存在导致TypeScript无法解析的多余字符；去除后全量构建暴露大量既有类型错误。已移除覆盖第三方真实类型的伪声明，保留严格检查，并修复单一路由入口、Redux类型推导、随访列表及审计页面部分真实类型错误。本轮最终构建仍有192条TypeScript诊断，包括领域契约、知情同意、设备等问题；数据为当次快照，需随代码变化重新运行构建。不能通过关闭严格检查或排除业务页面假装通过。

隔离的MongoDB测试容器只用于启动验证，不连接真实业务数据。`./start.sh` 在该实例下实际启动前后端，后端 `/health` 返回 healthy、MongoDB connected；浏览器访问首页和 `/auth/login` 显示仓库原有登录页面，未提交账号。登录页仍为本地账号流程，不能证明统一身份或认证API可用。结束后使用 `./stop.sh` 停止项目进程，确认测试数据库不被停止脚本控制，再结束临时数据库。

后续真实隔离实例中，Mongo断连时健康状态返回HTTP 207/degraded，恢复数据库后同一后端进程恢复HTTP 200/healthy。HTTP和WebSocket握手已统一访问令牌有效期、类型与账号启用检查，刷新令牌异常与存储检查已修复；本地四类演示账号经真实登录与 `/me` 验证。前端单一路由入口、令牌校验竞态和角色菜单已针对测试场景验证。这些是medicalassistant本地账号链路的验证，不代表113.44统一身份已接入。WebSocket会话成员/诊疗权限、消息持久化及连接中撤权尚未闭环；康复/Agent路由对象权限亦未完成，不能作为安全验收。

审计日志的列表、详情及近期记录已在隔离MongoDB和真实JWT下验证正反权限、读写审计、日期与排序；审计持久化失败不返回受保护数据。现有全局权限检查仍未实现显式自定义权限的完整语义，实时offset分页也不是冻结快照，需后续收敛。前端API根地址已规范，但部分资源路径和通信协议仍需独立修复。

实际启停测试暴露过Vite探测请求头问题和退出进程读取竞态；修复后11项隔离测试通过，真实进程重启并停止通过。现有服务在空数据库启动时会创建默认演示账号，且页面展示演示入口，不能用于真实患者或生产。前端正式构建仍未通过；首页可见不能证明全部路由、登录、业务流程或正式构建可用。两系统统一身份、113.44外部接口、临床规则、多中心授权与隐私计算均未实现或验收。
