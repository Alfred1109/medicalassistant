## 已修复的消息边界

`FormFillEmbedPage` 通过 iframe ref 获取实际 `contentWindow`，只接受该窗口发出的消息，并继续校验表单平台 origin、消息结构和非空会话标识。来自同源兄弟窗口、弹窗或其他父窗口的复制消息不能触发确认。确认仍由后端查询远端答卷状态完成。

验证：`node --test tests/form-fill-message.test.cjs` 的两项安全正反例通过；前端严格构建通过。当前证据为函数测试和构建，不替代真实浏览器跨站部署验收。

## 凭证持久化缺口（双端已闭合，2026-11-14 复核）

发现时源端 `app/routes/integration.py` 创建会话返回 `/integration/embed/<token>`，本地 `integrations/forms/models.py` 将完整 `embed_url` 同时保存在 `session` 和 `fill_sessions`，`GET /fill-tasks/{task_id}/embed-url` 再次返回该 URL；因此即使单独的 token 字段只存哈希，一次性凭证仍能从持久化 URL 中恢复，现有“明文不落库”注释并不准确。

复核确认两端均已按上述方向改造：源端创建会话（201）经 `_serialize_session` 只返回会话引用、状态与业务标识，不返回任何含凭证的 URL，模型中也没有 `embed_url` 字段或写入路径（测试断言响应不含 token/URL）；本地侧同样只保存会话引用，不再持久化或回传完整 URL。历史数据与历史文档中的 URL 盘点、脱敏迁移仍开放，见文末汇总。

不能只删除写入的 URL：目前任务列表按 task ID 打开嵌入页面，页面稍后向后端获取 URL；哈希无法还原启动凭证。需要双端契约同时调整，保留同一远端会话和同一草稿，而非通过新建任务掩盖恢复问题。

发现时源端一次性入口还是先查询状态再写 `embedded`，消费操作未使用原子条件变更；并发请求可能同时通过 `created` 检查。复核确认该问题已修复：源端消费与凭证轮换均使用条件 UPDATE（`status='created'` 且 `embed_token_hash` 匹配），并叠加 60 秒 `launch_expires_at` 短期窗口；独立 SQLite 并发测试验证并发双消费仅一次成功。

## 实现前置（源端代际已实现；本地全写者覆盖仍开放）

已确认要求是：项目或中心权限撤销、成员或账号停用后，即使后来恢复授权，旧链接和旧委托仍永久失效。发现时源端 `FillSession` 仅保存主体和资源 ID，没有记录可覆盖全部授权变更的代际；仅在每次访问时检查“当前有权限”，不能发现撤权后恢复的历史。复核确认源端已补上该机制：`FillSession` 现记录 `authority_generation`，源端以项目级 `bump_authority_generation` 单调递增代际并与业务变更同事务提交，Grant 撤销、成员撤销、客户端降级、中心停用、问卷关闭、受试者退出等变更入口已接入 bump（源端存在并行在途改动，此处只描述机制，不锚定行号）；打开、消费与委托请求中发现会话代际落后即拒绝。账号维度经源端 `auth_session_token` 轮换等效永久失效。仍开放：撤权后恢复授权/重新启用一类恢复场景的完整代际边界，以及本地端覆盖账号、项目成员、中心、客户端和资源授权全部写者的核验。

应先覆盖账号、项目成员、中心、客户端和资源授权的全部变更入口，建立单调授权版本或不可逆会话失效记录。会话绑定创建时的授权上下文，变更后旧会话不可恢复。ORM 事件或单个路由钩子若不能覆盖批量写、删除和重建路径，不能作为完整保证。

以下盘点针对本地端，全写者覆盖仍未完成：本地代码盘点显示写入分散于 `ProjectService` 的成员、中心和项目状态操作，`admin` 的账号修改/删除，表单关闭、版本及授权操作，客户端/Grant 变更，以及患者和受试者生命周期操作。成员重新启用可能清空 `revoked_at`，项目强制删除包含批量更新；因此不能把当前状态或单个 ORM hook 当作完整历史。还须逐项验证维护脚本和全部写者后才能声明覆盖完整。授权版本变化应和对应业务变更同事务提交，并保留已提交答卷及不可逆失效证据；普通资料变更不应无差别使全部委托失效。

## 双端启动与恢复方向

具备上述失效机制后，再实现以下契约并进行隔离端到端验证：

1. （双端已闭合，2026-11-14 复核）本地只保存会话引用、非敏感来源及状态，不保存含凭证的 URL。创建或启动响应中的短期凭证只在内存中透传，响应禁止缓存。
2. （双端已闭合）启动使用受控 POST，由源端核实客户端、真实操作者委托、当前资源权限以及会话授权代际。未消费的启动凭证可原子轮换哈希，旧凭证立即失效；消费也采用原子 `created → embedded` 条件。
3. （双端已闭合）已嵌入的会话通过无凭证恢复入口继续同一草稿。恢复入口必须依赖源端有效的受限 Cookie，核对同一会话、操作者及授权上下文；不能仅凭 session UUID 自动登录。Cookie 丢失时，按明确的重新认证委托流程恢复，不能回退为长期可复用链接。
4. （仍开放）历史 `session.embed_url` 和 `fill_sessions[].embed_url` 需要独立、默认 dry-run 的盘点和脱敏迁移；本轮未访问或修改现有业务库。

必要验收包括：全落库文档不含实际 token；旧 URL 不再返回；同源其他窗口拒绝；并发双消费只有一次成功；已有 Cookie 的同会话草稿恢复；无 Cookie 拒绝；撤权后恢复权限也不能复活旧会话；未知提交和远端失败不误报成功。测试中 URL 必须使用与 `embed_token` 相同的合成 token，避免字段分别断言漏掉 URL 泄漏。上述各项在隔离双应用测试与并发专项中已有覆盖，但证据仍是本地实现与合成环境，不构成真实 HTTPS、跨站 Cookie 与真实浏览器的部署验收，也不宣称跨端闭环已完成。

本轮仅完成消息窗口来源修复，未开放新的启动或恢复接口，也未改动源端或业务数据库。

## 本地续作：安全启动与草稿恢复

- 源端创建会话只返回引用，不返回启动凭证；康复侧也不存凭证或完整 URL。新 POST 启动在核实当前身份与原任务审核后取得短期凭证，浏览器使用临时表单将其 POST 给源端，凭证不进入地址栏；旧 URL 入口关闭。
- 源端对启动凭证轮换和消费使用条件更新，重复或过期凭证拒绝。已嵌入会话通过原受限 Cookie 及相同会话标识恢复；保存答卷时同事务记录真实答卷 ID，恢复时明确带该 ID，拒绝切换答卷。新会话需要源端 `launch_expires_at` 结构维护迁移，旧任务按原引用能力核查，不能把旧链接复活。
- 隔离双应用测试覆盖真实登录、单次启动、保存草稿、同一答卷及内容恢复、无 Cookie 拒绝和 Mongo 不保存启动凭证；独立 SQLite 并发测试验证双消费与双首次保存各仅一次成功。浏览器测试使用实际前端和合成 API、临时自签名 TLS，验证刷新恢复与确认失败时保留填写内容；不是正式网络环境或真实源端浏览器验收。
- 现存历史文档中的 URL 未盘点、脱敏或迁移；创建超时的幂等对账、授权代际全写者覆盖、真实 HTTPS 与跨站 Cookie 浏览器兼容仍需完成。创建超时幂等对账在源端同样缺失：源端无幂等键，也没有按 `ma_task_ref` 的查询端点。旧凭证若在切换前已泄漏，还须通过源端会话失效及迁移处理，不能仅靠本地接口退役视为消除。填报保持默认关闭。
